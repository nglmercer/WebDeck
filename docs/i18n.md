# Typed translations

Edit `frontend/locales/<locale>.ts`. `en_US.ts` defines the message structure and English fallback. Every shipped non-English catalogue uses `satisfies CompleteLocale` to require every canonical leaf. All seven supported languages must be complete. Locale IDs such as `en_US` and `es_ES` stay unchanged in saved settings.

Messages are grouped by purpose: `common`, `editor`, `audio`, `keyboard`, `connections`, `devices`, `guides`, and other feature namespaces. Reuse a shared key when the meaning is the same. Keep distinct keys when context requires different wording.

```ts
// frontend/locales/en_US.ts
export default {
  common: {
    save: 'Save changes',
    cancel: 'Cancel',
  },
  audio: {
    fragment: 'Fragment',
  },
  // Other groups and locale metadata…
} as const;
```

## Using messages

```ts
import { common, keys, useTranslations } from '../../lib/i18n';

const t = useTranslations();
const { audio } = keys;

t(common.save);
t(audio.fragment);
t('audio.fragment');
t(keys.deck.editNamedButton, { label: button.label });
```

Constants and dotted paths are checked against the English catalogue. Misspelled paths and namespace objects fail TypeScript checks. Keys are paths, not English text. The key tree is derived from the same catalogue, so it does not require a second authored list.

Local validation failures carry message keys. Use `t.message(error.message)` only for runtime text, such as an external server failure, which might not have a known key. Unknown text remains readable. English strings are not lookup aliases. Svelte escapes the returned text; translations are not rendered as HTML.

`{name}` and `%name%` interpolation both work. Preserve placeholder names in translated values so each language can choose its own word order. User content, IDs, tokens, protocol enum values and plugin arguments remain data.

## Adding or editing a locale

1. Add or edit values in `frontend/locales/<locale>.ts`. A new locale needs `meta.nativeName`, `meta.englishName`, `meta.langCode`, `meta.authorName` and `meta.authorGithubUsername`.
2. Import `CompleteLocale` from `./schema` and use `satisfies CompleteLocale`. Translate every leaf, preserve placeholders, and add the locale to `tools/i18n/coverage-policy.json`. The shared reader rejects undeclared or partial shipped catalogues.
3. Run `npm run i18n:generate --prefix frontend` to update the JSON consumed by Rust.
4. Run `npm run check:i18n --prefix frontend`, `npm run check:components --prefix frontend` and `npm test --prefix frontend`.

Development and production Vite builds generate the JSON automatically. The development server watches the TypeScript locale directory and regenerates JSON when a locale changes. Validation checks duplicate properties, supported message values, unknown keys, placeholder parity, untranslated markup and generated JSON freshness.

Only the English catalogue is imported by the application bundle. Other locales are fetched through the session's translation endpoint.

## JSON and Rust

`webdeck/translations/*.json` are generated transport files; do not edit them directly. The shared serializer converts nested TypeScript objects to a flat JSON dictionary:

```json
{
  "common.save": "Guardar cambios",
  "audio.fragment": "Fragmento",
  "meta.langCode": "es"
}
```

Rust already parses these dictionaries with `serde_json` and overlays the selected locale's leaves onto English. The merge remains defensive if a runtime dictionary omits a value, but the shipped source catalogues must include all groups and leaves. The API remains `Record<string, string>`; no TypeScript parser or new write endpoint is needed in Rust. The frontend fallback and JSON exporter use the same serialization function, and there is no separate generated English fallback module.

Development reads JSON from disk. Release builds generate and embed the JSON and locale list alongside the frontend. Missing or invalid selected locale files fall back to English. Safe locale basenames prevent filesystem traversal. The retired translation entries and `ui_*` aliases have been removed.

## Verification and known test failures

The migration passes 102 frontend unit tests, three serializer tests, 84 browser checks, the Rust locale-merge regression, and the component, type, translation, contract, formatting and bundle checks. An isolated development-server fixture verifies that editing a TypeScript locale updates JSON and deleting a locale removes its generated export.

The full deck browser suite still has ten existing failures involving outdated editor selectors and touch target sizes. All ten also reproduce on the previous commit, `ad86e97`, in an isolated checkout with the same native binary, dependencies and browser. They are listed with the validation and bundle measurements in [the migration evidence](v2/evidence/improvements/typed-i18n.json); the passing deck run explicitly excludes those ten cases.


## Coverage checks

Every shipped locale uses `CompleteLocale`, so adding an English leaf requires translations in all supported languages at type-check time. `tools/i18n/coverage-policy.json` declares complete locales and the reviewed message paths that legitimately match English (protocols, brands, shared words and placeholder-only formats). The shared catalogue reader rejects omissions in complete locales and unreviewed copied English in authored translations. Per-leaf English fallback remains defensive support for runtime dictionaries and external integrations; shipped catalogues may not depend on it.

Run `npm run i18n:audit --prefix frontend` for counts across all languages, or `npm run i18n:audit --prefix frontend -- --json` for every missing key and unchanged authored value. `npm run check:i18n --prefix frontend` also checks visible literal text in markup, text expressions and accessible attributes. User content, backend diagnostics and external plugin names are not translated by guessing at English strings.


The native tray menu reads the same JSON dictionaries through `server::translations`; it reuses the Settings, QR and Exit message paths and adds `common.openWebDeck`. The selected language is read from the existing configuration store, and menu text refreshes on native event processing after a language change. Rust performs no TypeScript parsing and maintains no second translation table.

Coverage and validation results for all supported languages are recorded in [the i18n audit](v2/evidence/improvements/i18n-coverage.json). Mobile editor captures are included for English, Spanish, German, French, Korean, Polish and Russian.
